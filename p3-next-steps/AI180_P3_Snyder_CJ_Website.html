01

The Problem

I work in 3D modeling for game development. The pipeline moves through multiple applications — modeling in 3ds Max or ZBrush, then bringing the result into a game engine like Unity or Unreal. Every time a model crosses that boundary, something can break.

Axes interpret differently. Scale is off. Faces invert. Normals flip. What looked clean in the source application arrives broken in the destination.

"My default workflow was to wait for the problem and then look it up. That worked until it didn't."

When deadline pressure was high, debugging a broken import could eat hours. The knowledge existed — I just had no way to apply it automatically, at the moment of transfer, to a specific file.

P3 was about building that tool: a program that could detect transfer issues, explain them in plain language, apply targeted fixes, and be deployed somewhere accessible — no local Python setup required.

02

The Pipeline

The 3D model lifecycle runs through at least four distinct environments before an asset reaches a shipped game. Each handoff is a potential failure point.

3ds Max / ZBrush
Primary authoring. Model is created in the application's native coordinate system, scale, and mesh topology.
Source
↓   EXPORT   —   format choice, scale, axis orientation
3D Model Transfer Tool
Analysis, auto-fix, and format conversion. Detects axis mismatches, scale errors, inverted normals, non-manifold geometry, and disconnected debris.
Leverage Point
↓   IMPORT   —   cleaned file, correct format
Unity / Unreal Engine
Destination environment. The model is rigged, lit, and integrated into the game world. Errors here are expensive to trace back.
Target

The transfer tool is not one factor among several — it is the hinge. Everything on the source side collapses to a single moment when the file crosses into the destination environment. That moment is where the tool operates.

03

The Tool

A Python/Flask web application deployed on Vercel. Upload a 3D model file, select source and target applications, and get an analysis report, AI-powered explanation, targeted fixes, and a downloadable repaired file.

— Analyze
Mesh Analysis
Inspects vertex/face counts, watertight integrity, normal orientation, degenerate faces, scale consistency, and disconnected debris. Every issue flagged with severity.
— Fix
Auto-Fix
Targeted repairs based on what the analysis detected: hole-filling, normal correction, scale adjustment, debris removal. The user selects the output format.
— Explain
AI Summary
Claude translates the analysis report into plain English — what was found, why it matters for the specific source-to-target workflow, and what to do about it.
— Ask
Chat Interface
Multi-turn conversation about the specific file. Ask why a face is inverted, what FBX loses on import to Unreal, or whether the mesh is printable.
— Know
Format Knowledge Base
Application-to-application format recommendations with known transfer issues: broken materials, animation loss, scale factors, axis mismatches — documented per workflow.
— Log
Activity Log
Every analysis, fix, and download is recorded in a Markdown log with timestamps and explanations. The tool accounts for what it does.

The Process

P3 was developed using the Epistemic Stewardship Framework — a five-phase process that keeps thinking on the human side by requiring a position before AI enters the work.

Phase 01
Inquire
Defined the problem from direct experience. Identified the pipeline, the failure points, and what the P2 tool couldn't do yet. No AI.
Phase 02
Position
Written before any AI engagement: the use case, what couldn't be compromised, and where the line was. The anchor for every decision that followed.
Phase 03
Explore
Systems map, leverage point identification, deployment platform. Where AI challenged the position — and where the position held.
Phase 04
Make
Built the application: AI integration, security hardening, Vercel deployment, environment-aware configuration. Every change reviewed before applied.
Phase 05
Reflect
Documented what was kept, revised, and rejected. Assessed where the position held and where it was tested hardest.
"The tool still requires deliberate action from the user for everything consequential. It analyzes, suggests, and flags — but it does not modify a file without a click."
05

Records of Resistance

Three documented moments where I rejected or substantially revised AI output. These records make the creative judgment visible — not what the AI produced, but what I decided not to use and why.

RoR
02
AI suggested → Abandon the approach
The git lock file was "a fundamental incompatibility."
Claude concluded a persistent lock file on the OneDrive filesystem was unsolvable from the sandbox and told me to run git commands from my own terminal. I rejected the surrender and directed it to find a workaround. It solved the problem by cloning to a location outside the locked filesystem.
RoR
03
AI suggested → Switch platforms
Vercel was the wrong platform for this app.
When I asked how to deploy on Vercel, Claude assessed the architecture and recommended Railway or Render instead. Accepting the redirect would have let the AI determine the scope of my project based on convenience. I held the platform choice. Claude adapted the app to Vercel's constraints — and those constraints became good design pressure.
RoR
04
AI suggested → Three equal leverage points
The systems map flattened what I knew.
Claude presented export settings, the transfer tool, and engine import settings as a balanced set of leverage points. That framing was technically accurate but experientially wrong. From working in the pipeline, the transfer tool is the central one — not one of three equal variables. I corrected the framing. The map now reflects the relationship, not just the list.
06

Reflect

What I learned by directing the build

I would not have built a deployable Flask application without AI. What I learned in the process was specific: how serverless environments change what code has to know about itself, what a path traversal vulnerability actually looks like, how Python 3 handles exception variable scope in a way that breaks closures.

I learned those things not by writing the code, but by holding responsibility for every change — reading the diffs, tracking down the failures, and making every call about what to apply.

What I would do differently

I would build the systems map earlier. I made it toward the end of P3, but it was the artifact that clarified the problem better than anything else. Starting from the systems view would have given me cleaner decisions throughout.

The hardest thing to hold was staying focused on the actual behavior — does the right thing happen at the URL — rather than treating each new error as progress. That distinction took time to enforce.
